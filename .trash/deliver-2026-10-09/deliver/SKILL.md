Доведи согласованную задачу до проверенного изменения. Маршрут идёт в новом окне по документу handoff из аргументов. Без пути выполни [handoff](../handoff/SKILL.md) по текущему разговору, вместо его предложений выведи одну команду `/deliver <путь>` для нового окна отдельным fenced-блоком без языка и остановись. С путём прочитай документ и учитывай последующие поправки пользователя. Открытые продуктовые решения согласуй по [grilling](../grilling/SKILL.md), до зависимой работы.

Это оркестратор: читай SKILL.md нужного этапа и выполняй его инструкции; не ограничивайся упоминанием команды. Внутри маршрута предложения следующей команды от этапов не выводи: переходами управляешь ты. Скиллы остаются доступны отдельно.

До апрува результата не запускай ship, не коммить, не пушь и не создавай PR в трекере. Не сливай PR. Пользовательские изменения сохраняй.

## Продолжение

В начале работы добавь в документ раздел «Продолжение»: рабочий каталог, текущий этап и следующий шаг, открытые вопросы, ограничения на коммиты и публикацию; обновляй его по мере работы — выполненное и подтверждённые проверки. Принятые решения и ещё не внесённые в проект записи держи в документе, а не только в истории чата. Если окно потеряно или контекст перегружен, продолжай `/deliver <путь>` в новом окне с этапа из «Продолжения», без повторения завершённого.

## Маршрут

1. Актуализируй документ принятыми поправками, не создавай копию. Он хранит общие решения и записи для документов проекта; не подменяй им постоянные SPEC.md.
2. Выполни [review-plan](../review-plan/SKILL.md). Исправь подтверждённое, спорное согласуй. Не переходи к реализации, пока существенные вопросы открыты.
3. Разбивай задачу, если она содержит несколько самостоятельно проверяемых результатов или её нельзя разумно выполнить одним исполнителем в одной сессии. Тогда выполни [to-tickets](../to-tickets/SKILL.md). Для небольшой задачи используй исходный документ как единственную задачу.
4. Зафиксируй исходные git status и diff, чтобы отличать работу задачи от чужих изменений. Запускай отдельного исполнителя на каждую готовую задачу последовательно в текущем рабочем дереве. Следующую начинай после проверенного завершения её зависимостей. Передай исполнителю [implement](../implement/SKILL.md), общий документ, тикет, рабочий каталог и границы правок; требуй отчёт с проверками и запрет коммитов. Общие решения передавай ссылками. Исполнители не задают вопросы пользователю напрямую: нерешённое возвращают тебе. Помечай тикет выполненным по коду и проверкам, а не по утверждению исполнителя.
5. Запусти отдельного ревьюера в свежем контексте на всё изменение, включая новые файлы и стыки тикетов. Передай [review-changes](../review-changes/SKILL.md), общий документ, тикеты и исходный diff; режим только находок, без правок, вопросов, повторного запуска проверок и предложения команд. Флаг `--external-reviewer` не передавай: внешнего ревьюера другого агента ревьюер запускает сам по review-changes.
6. Сверь находки с кодом. Однозначное исправь через исполнителя; спорное согласуй по grilling. Проверь затронутое после исправления; при существенных исправлениях повтори независимое ревью затронутого. Обновляй в документе выполненное, проверки и нерешённое. Не объявляй готовность с открытыми существенными находками.

Если отдельные агенты недоступны, сообщи об ограничении; не называй собственную проверку независимым ревью. Не заменяй отдельные контексты запуском другого CLI с выбранной тобой моделью без просьбы пользователя.

## Результат и публикация

При подготовке описания PR прочитай и примени [show-me](../show-me/SKILL.md) к окончательному коду после исправлений по ревью.

Сохрани в каталоге документа задачи `PR.md`: заголовок и готовое описание PR — проблема и результат, подтверждённые проверки, возможность отката и область последствий. Схему и сравнение до/после добавляй, когда они помогают оценить изменение. Не выдавай запланированную проверку за выполненную. В документе задачи добавь раздел «Публикация PR» со ссылкой на `PR.md`; целевую ветку бери из правил и настроек проекта, неоднозначность согласуй.

Сначала выведи подготовленный заголовок и описание PR, затем отчёт ревью (находки, исправления, оставшиеся вопросы или «Находок нет»), результаты проверок и ссылку на документ задачи. Остановись для апрува результата. «Ок/+» на предыдущие решения не разрешает публикацию ещё не показанного результата.

После явного апрува показанного результата выполни [ship](../ship/SKILL.md) с документом задачи: проверки, коммиты, push, публикация подготовленного PR. Если ship изменил код, актуализируй PR и проверь вызванные изменением риски; существенное изменение согласованных решений требует нового апрува. В конце дай ссылку на PR.
